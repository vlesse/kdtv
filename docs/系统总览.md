## 1. 这是什么

**给酒店客房做的机顶盒电视系统。** 一台安卓盒子插在客房电视后面，客人拿遥控器
就能看直播频道、点电影、点客房服务；酒店在网页后台管房间、看订单、改菜单；
平台（也就是这套系统的所有者）一套服务器管很多家酒店，按酒店收服务费。

### 1.1 它解决的问题

酒店电视这件事的常规做法有三种，每一种都有一个具体的痛：

| 常规做法 | 痛在哪 |
|---|---|
| 就用有线电视 | 频道是当地台，外国客人看不懂；点播、点餐、酒店自己的品牌全都没有 |
| 买一套商用 IPTV | 一次性几十万，绑死一家供应商，改一行字要提工单等两周 |
| 每间房装个电视盒子随便配 | 客人能退出去乱逛、能装东西、能看到上一个客人的账号；改任何东西要挨个房间跑 |

这套系统对应的三个决定：

1. **内容从一台 XUI.one 面板来**（Xtream-codes 生态的流媒体面板）。频道和片库
   都在面板上，换片源不动业务代码。
2. **界面和规则都在服务端**，盒子里的 APK 只是一个薄壳。改菜单、改价格、换模板、
   改首页背景 —— 部署一次服务器，所有电视下次开机（或者十五分钟内自己）就变了。
3. **一套服务器多家酒店**，每家的房间、菜单、品牌、收款、片库互相看不见。

### 1.2 它满足的功能

- **直播**：面板上的频道，带分类、台标、节目单（EPG）、**每个频道一段会动的
  预览图**（不是第二条视频流，见 §6.3）
- **点播**：电影和剧集一张货架，海报墙、详情、分集、**能快进能拖进度条**、
  拼音首字母搜索（遥控器上没有中文键盘，见 `bff/src/pinyin.js`）
- **受限板块**（成人内容）：按房间授权 + PIN + 服务端强制，三道门（§6.4）
- **客房服务**：电视上点餐 → 前台手机上接单；支持在线收款（扫码）或者挂账
- **旅游周边**：酒店附近的去处，四语言，后台可编辑
- **多语言**：中文 / English / ខ្មែរ（高棉语）/ Indonesia
- **两套电视模板**：`portal`（首页宫格）和 `live`（开机直接全屏直播）
- **计费两种模式**：酒店付服务费（客人免费），或者酒店不付 → 客人自己按天买
- **后台**：房间和设备、菜单和订单、品牌和背景、收款、面板、账号和操作记录
- **前台手机页**：开房、退房、接单 —— 站着用，一只手
- **装机页**：`/download` 给二维码、版本、大小、SHA-256 和装机步骤

### 1.3 现在的规模（2026-09-20）

| | 数 |
|---|---|
| 直播频道 | 91 |
| 面板上的电影 / 剧集 / 分集 | 6745 / 749 / 13318 |
| 线路能看到的电影 | 6046 |
| 电视上的非成人片库 | 1658 |
| 支持的语言 | 4 |
| 并发上限 | 线路 500 连接（即 500 个同时在看的房间） |

## 2. 一句话记住的架构

> **内容在面板，规则和界面在 KDTV 服务器，盒子只是一个壳，视频不经过我们。**

```
                          ┌──────────────────────────────┐
  客房电视              │  KDTV 服务器 (<APP_HOST>)      │
  ┌──────────┐          │                              │
  │ 安卓盒子 │──① 开机报到─▶ BFF (Node/Fastify/SQLite) │
  │  APK 薄壳 │◀─② 界面+数据─│   房间 订单 收款 权限 多租户 │
  │ (WebView) │          │   电视界面(web bundle)        │
  └────┬─────┘          │   后台 /admin/  前台 /desk/    │
       │                 └───────────┬──────────────────┘
       │                             │ ③ 只问元数据（频道表、片单、播放地址）
       │                             ▼
       │                 ┌──────────────────────────────┐
       │                 │  XUI.one 面板 (<PANEL_HOST>)  │
       │                 │   频道源、电影、剧集、线路     │
       │                 └───────────┬──────────────────┘
       │                             ▲ ⑤ 采集器直连 MySQL 写片库
       │                             │   (xui-collector，另一个仓库)
       └──④ 视频直连上游 CDN ─────────┘
              （302 之后就跟我们无关了）
```

四件事分别在哪：

| 东西 | 在哪 | 换掉它要动什么 |
|---|---|---|
| 频道和片库 | XUI 面板 | 面板是 `panels` 表里的一行，每家酒店各指一台（`bff/src/panels.js`） |
| 业务规则 | BFF | 这个仓库的 `bff/` |
| 电视界面 | web bundle，由 BFF 发 | 这个仓库的 `web/`，部署即生效 |
| 视频字节 | 完全不在我们手上 | — |

**为什么视频不走我们。** 面板上每个流都是 `direct_source=1`：面板只回一个 302，
盒子拿着 302 直接去上游 CDN 取。如果让视频穿过 BFF，那台机器的带宽立刻变成整个
系统的天花板 —— 500 个房间同时看，没有任何一台普通 VPS 扛得住。例外只有一个：
少数上游不给 CORS 头，浏览器（不是盒子）够不着，那几条走 `relay.js` 中继（§6.2）。

**为什么界面是网页。** 三条需求塌缩成同一个决定：要跨平台 → 网页；要热更新 →
服务端部署一次全车队生效；客人不该输服务器地址 → APK 里只烧一个地址，别的全从
那里取。代价是播放层受浏览器限制，这个代价量过（`shell/probe/RESULTS.md`）。

## 4. 数据模型

一个 SQLite 文件，全部表在 `bff/src/db.js`。选 SQLite 不是图省事：这套系统的
写入量是「几百个房间偶尔点个餐」，而少一个要运维的进程在酒店这种环境里是实打实
的可靠性。

```
properties（酒店）──┬── devices（盒子）──── rooms（房间）
     多租户的根       ├── service_items（菜单）── orders（订单）── payments
                      ├── explore_spots（周边）
                      ├── settings（品牌/背景/计费/收款，按酒店分）
                      ├── media（上传的图片视频）
                      └── notices（通知）
panels（接了哪几台面板）◀── properties.panel_id / devices 各自的线路
admin_users ── admin_sessions ── admin_audit ── admin_lockout
art_cache（海报缓存的账本）
```

| 表 | 存什么 | 关键点 |
|---|---|---|
| `properties` | 一家酒店 | **多租户的根**。所有查询都带 `property_id` |
| `devices` | 一台盒子 | 主键是设备号（ANDROID_ID）；带配对码、MAC、房号、线路、成人授权、观看权 |
| `rooms` | 一间房 | 住客姓名、入住退房。客人不是「用户」—— 没有账号，三天就走了 |
| `service_items` / `orders` | 菜单 / 订单 | 四语言菜名、价格、币种；订单状态 `new → ...` |
| `settings` | 键值 | **env 是默认值，这张表里的行覆盖它**，按 `property_id` 分 |
| `panels` | 一台面板 | `slug='default'` 那一行是平台默认。**改 .env 不会动它**（§11 陷阱 1） |
| `admin_users` | 后台账号 | scrypt 存密码；角色 `platform` / `manager` / `desk` |
| `admin_sessions` | 登录换的票 | 存 sha256，不存原文；空闲 7 天 / 绝对 30 天 |
| `admin_audit` | 谁动了什么 | 只记写操作；密钥类字段只记名字不记值 |
| `art_cache` | 海报缓存账本 | 键是原图地址的 sha1 前 20 位 |

**客人不是用户，房间才是单位。** 三样东西各自决定电视上的一件事，分开是这栋楼
能管起来的原因（`bff/src/rooms.js` 顶上那段）：

1. **线路（line）** —— 面板上的一个账号，决定**片库**（看得到哪些频道和片子）
2. **房间（room）** —— 决定**招呼**（欢迎语、住客姓名）和订单归属
3. **授权（flags）** —— 决定**能不能看受限板块**、观看权买到哪天

## 5. 一台盒子的一生

### 5.1 出包

APK 里烧死的只有一个东西：**服务器地址**。

```bash
cd shell && ./gradlew assembleRelease -PportalUrl=https://ott.example.com/
```

签名钥匙不在仓库里（查找顺序见 `shell/app/build.gradle.kts` 顶部）。
**签名和包名都是不可逆的**：换签名 = 每台盒子的 ANDROID_ID 全变 = 房间、成人
授权、观看权一起丢；换包名 = 对已装机的电视来说是另一个应用，只能手工卸载重装。

### 5.2 装机

三条路：盒子上浏览器敲 `ott.example.com/apk`（短地址，遥控器敲得动）、U 盘、
或者 adb 批量预装。装完建议**同时**做两件事：开机广播（APK 里已经有）和
**把 KDTV 设成默认桌面** —— 后者更可靠（Android 10 之后有些固件会静默拦掉后台
启动），而且顺带挡住客人乱逛系统设置，酒店真正想要的是这个。

### 5.3 第一次开机 → 配对

```
盒子通电
  └─ APK 起来 → WebView 打开 PORTAL_URL
       └─ web bundle 加载 → main.ts boot()            [web/src/main.ts:308]
            └─ POST /api/device/hello {deviceId, mac}  [bff/src/server.js:87]
                 ├─ 库里没见过 → 建一行，发一个六位配对码
                 └─ 回 {activated:false, pairingCode:"482913"}
                      └─ 屏幕上显示那六位数，等人来绑
```

**客人永远不需要输服务器地址。** 设备号来自 JS 桥（`web/src/api.ts` 从 APK 注入的
`KDTVShell` 取 ANDROID_ID），配对码是给运营看的，不是给客人看的。

有网线的话 MAC 也会一起报上来 —— 可以提前把 MAC 和房号录好，盒子一插电就自动
进对应房间，**装一栋楼的时候这个差别很大**。

运营在后台「房间和设备」里给这台盒子填房号并保存
（`POST /api/admin/devices/:deviceId`）。那一刻盒子会被划给这家酒店
（`devices.property_id`），拿到线路，`hello` 从此回 `activated:true`。

### 5.4 开机时序（已激活）

`boot()` 的顺序是被现场逼出来的，每一步都有理由：

```
① 退避重试 hello，最多约一分钟   [BOOT_RETRIES = 1s,2s,4s,8s,15s,15s,15s]
     └─ 为什么：电视通电之后，我们这个应用常常比 Wi-Fi 关联、比网线拿到 DHCP
        更早跑起来。第一次 hello 失败几乎是必然的。这一分钟里屏幕上还是那个
        转圈 —— 客人看到的就是「电视在开机」。一分钟还不通才值得摆错误页。
② 拿到 session：这台盒子属于哪家、哪间房、能不能看受限板块、有没有周边
③ GET /api/channels          → 频道表和分类（服务端按线路缓存，面板只看见一个调用者）
④ GET /api/app/home          → 酒店的品牌、背景、模板、播放档位（**拿不到不挡开机**）
⑤ void loadVod()             → 片库**踢出去后台跑，不等它**
⑥ showHome()                 → 上屏
```

**第 ⑤ 条是一个真实缺陷的修复。** 片库那一条接口要把电影、剧集和两套分类都拉
回来，实测两秒上下；开机等它 = 客人对着黑屏多等两秒，而首页上五格里有四格跟
片库毫无关系。所以开机不等，点播那一格自己负责显示「还没到」。

### 5.5 首页

两套模板，后台选（`/api/admin/tv`）：

- **`portal`** —— 宫格：直播、点播、客房服务、旅游周边、（受限板块）、关于。
  底部一条导航条，尺寸全部从 `--u` 一个变量推出来（1266px 稿子上是 163px），
  所以 1366 和 1920 上比例一致，而不是每个 `clamp()` 各自缩放。
- **`live`** —— 开机就是全屏直播，按菜单键才出频道表。给「只想要电视」的酒店。

所有「返回首页」都走同一个入口 `showHome()`：模板 B 根本没有首页，漏判一处客人
就会在某个屏幕上按返回掉进另一套界面。

首页开着的时候会**每 60 秒问一次权限**（`watchEntitlements`）：运营刚在后台给
这间房开了受限板块，客人不用重启电视，一分钟内那一格自己长出来。（这一条是
漏掉过的 —— 原来只在开机时读一次，运营授权完盯着电视什么都没发生。）

### 5.6 界面自己更新

WebView 只在开机那一次去取页面，之后一直跑着。也就是说部署完，墙上那台电视
还是旧界面。`web/src/updater.ts` 每 15 分钟问一次服务端算出来的**页面指纹**
（不是 `APP_VERSION` —— 那是环境变量，部署不会动它），变了就在**没人用的时候**
重新加载：没在播放、没有浮层开着、最近三分钟没人按遥控器，三条都要过。

## 6. 播放链路

### 6.1 直播

```
客人按 OK
  └─ GET /api/play/:streamId                        [bff/src/server.js:369]
       ├─ billing.allowed(dev,'live')  否 → 402     [bff/src/billing.js:102]
       ├─ adult.playAllowed(...)       否 → 403     [bff/src/adult.js:376]
       └─ 回 {url: "<面板>/live/<user>/<pass>/<id>.m3u8"}
            └─ 盒子请求它 → 面板回 302 → 上游 CDN → 视频
```

两道门都在**播放这一步**再查一次，不是只在列表那一步：分类 id 是连号的，接口
在公网上，猜一个 id 不能成为绕过 PIN 或者绕过付费的路子。

**为什么播放地址指向我们的域名再跳。** `XUI_PUBLIC_BASE` 指的是
`https://ott.example.com/stream`，nginx 把它转给面板。这看起来像在代理视频，
其实不是 —— 面板只回 302，nginx 搬的是一个重定向头。这样买到两件事：
线路口令不在酒店的网络上明文跑；页面是 HTTPS，第一跳也是 HTTPS。

### 6.2 中继（只有浏览器用）

`?relay=1` 的意思是「我自己取不到」。两种客户端会这么说：浏览器从一开始就
取不到（跟不了到明文 HTTP 的 302）；盒子只在**试过之后**才说 —— 它跟得了 302，
但播放器是用 XHR 读播放列表的，而 91 个台里有三个上游完全不给 CORS 头。

关键在于**这是客户端提的请求，不是服务端嗅出来的**：只有客户端知道自己刚才
失败在哪。**车队的视频因此永远不经过我们这台机器**，只有那三个台的浏览器访问
会走 `relay.js`。

### 6.3 频道预览动图

频道卡上原来只有台标和名字，客人划过 91 个台，没有任何线索告诉他此刻哪个台在
放什么。解法是 ffmpeg 预先截好的 **animated WebP**（480x270 / 15 帧 / 1.5 秒 ≈
49KB）：浏览器当图片解，**完全不碰媒体解码器** —— 机顶盒的硬解码器只有那么
几个，多开一个给预览就少一个给正片。

去重按「线路 + 面板」而不是按酒店：十家酒店共用一条默认线路是常态，按酒店扫
就是同一批频道抓十遍。受限频道一张都不生成（图片落在公开目录下）。

### 6.4 点播

```
GET /api/vod            电影和剧集**一张货架**（面板分两个命名空间，在这里合并）
GET /api/vod/:kind/:id  详情（简介、年份、分集）
GET /api/vod/play/:kind/:id   同样两道门 → 播放地址
```

点播页的两个真实缺陷和它们的修法：

**① 点「点播」要等 5-6 秒。** 原因是同步构造 925 张海报卡的 DOM。改成
「先上屏，再分批填」（`drain()`）—— 按下去立刻换屏，剩下的自己长出来。

**② 海报大面积不显示。** 原因不是图大（一张才 20KB），是**每一张都要盒子自己
去跟一个陌生图床握一次手**：实测单张 DNS+TCP+TLS 就去掉一秒多，而 HTTP/1.1 下
浏览器对同一个域名最多开六条连接。九百张排队，客人翻页比它快得多。

改成 `bff/src/art.js`：**服务端去取一次，存在本机，所有房间共用。**
`proxy(url)` 把第三方地址换成 `/api/art/<sha1 前20位>`，`warm()` 在每次
`/api/vod` 之后四路并行预热（一轮 1500 张，10 分钟节流），`sweep()` 清 60 天
没人要的。盒子只跟我们这一个域名打交道 —— 那条连接它本来就有；加一年的缓存头，
同一台盒子第二次进点播连请求都不发。

**进度条和快进**（`web/src/vod.ts`）：进度条本身是一个可聚焦元素，带
`data-autofocus`，所以点进去焦点就在它上面 —— 「快进没反应」当初其实是焦点在
别的地方。左右方向键跳，数字键 0-9 跳到百分之几十，也支持媒体键和点击。
`SEEK_SETTLE_MS = 350` 是连按的合并窗口。

### 6.5 受限板块（三道门）

一家带成人内容的酒店必须能回答三个问题，`bff/src/adult.js` 顶上那段就是这三个：

| 门 | 是什么 | 在哪 |
|---|---|---|
| ① 这间房能不能有 | **按盒子授权，默认关**。家庭楼层、宿舍、有小孩的房间干脆没有这个板块，PIN 也变不出来 | `deviceAllowed(dev)` |
| ② 拿遥控器的人能不能看 | PIN，**在服务端查**，不在电视里查。错五次锁一段时间 | `unlock(dev, pin)` |
| ③ 有没有别的路进去 | 没有。列表里藏一个分类挡不住任何人 —— 流 id 是连号的，接口在公网上。所以**上锁的分类在播放那一步被服务端拒**，不是在界面上被藏起来 | `playAllowed()` / `restrictedIds()` |

受限分类是按**面板的分类 id** 存的（`vod:43` 这样），不是按名字 —— 这一条在
换面板的时候是个陷阱（§11 陷阱 2）。

解锁之后要重取整份片库，**而解锁之后那一份大得多**（这条线路上四千多部是成人
分类的，平时发下来的只有一千六百多）。所以按完 PIN 的顺序必须是：先同步立起
「正在加载」，立刻上屏，再等数据 —— 不能是「按完 PIN 对着一片黑等」。

## 7. 钱

### 7.1 三种钱，一条管子

`bff/src/pay.js` 收三种钱，**下单、出码、回调、查单、对账完全共用**：

| kind | 谁付给谁 |
|---|---|
| `service` | 客人付酒店 —— 电视上点的客房服务 |
| `unlock` | 客人付酒店 —— 自己买的观看权（只有酒店不付费时才出现） |
| `property` | 酒店付平台 —— 按期的服务费 |

拆成三套的诱惑很大，但那意味着**同一个回调校验写三遍**，而回调校验写错一次就是
「谁都能把订单标成已付款」。

两条铁律：**金额只认回调里的**（不认客户端传的），**发货必须幂等**（同一笔回调
来十次只发一次货）。

网关是 Jeepay（自建聚合支付，对下游接支付宝/微信/银行/加密货币）。签名规则是
最容易错也最难查的地方（网关只回「签名错误」四个字），五步全写在
`bff/src/jeepay.js` 顶上。

### 7.2 点餐下单的顺序

```
客人在电视上选好 → POST /api/service/order          [bff/src/server.js:650]
  ├─ 逐条核对菜品：**必须是这家酒店的、上架的**（猜到别家的 id 也没用）
  ├─ 先把订单写进库（status='new'）
  └─ 再试着挂一笔收款
       ├─ 网关没开 / 币种对不上 / 建单失败
       │    → **订单照样成立**，按未付款留给前台
       └─ 成功 → 电视上出二维码，客人扫码付
```

**收款是挂在订单上的，不是下单的前提。** 一个因为网关抽风而消失的客房服务订单，
等于一个以为没人会来的客人。

### 7.3 谁出钱（`bff/src/billing.js`）

一个开关的两面：

- **酒店付费**（默认）：酒店按期付服务费，客人什么都不用付，电视上连收款的
  影子都看不见。
- **客人付费**：酒店没付（或者压根不打算付），住客自己按天买观看权，跟着这台
  盒子走。

两者不是两套代码，是同一个判断的两个分支：`allowed()` 先看酒店付了没有，没有
才去看这台盒子自己买了没有。**酒店服务费到期那一刻电视不会黑屏**，只是从「免费」
变成「客人自己买」。

付费墙挡的是**播放**，不是**目录** —— 看不见自己要买什么的客人没有理由买。

## 8. 内容从哪来

```
资源站 ──采集──▶ XUI 面板 ──线路──▶ 盒子
```

- **直播频道**：面板里配好的源（91 个）。
- **电影和剧集**：`xui-collector`（**另一个仓库**）从资源站抓进面板。面板发来时
  目录是空的。

采集器的两个要点（踩过）：

1. **它直连面板的 MySQL 写表**，不走 API —— 所以它认的地址是 `XUI_DB_HOST`，
   和 BFF 认的 `XUI_BASE` 是两码事。
2. **写进去的流要被勾进线路订阅的套餐里才对车队可见**，而套餐是在一次运行的
   **结尾**才一次性更新的 —— 跑到一半去看 `player_api` 的数字不动是正常的。
   之后面板自己的 `cache_engine` 五分钟内会认到。

采集器的账本（`items` 表记「这个源条目对应面板上哪个流 id」）**会自愈**：
换了面板之后那些 id 不存在了，它每次先 `movieExists()` 确认，不存在就重新插入
并更新账本 —— **不需要手工清表**。但增量模式只走最近几页，老条目不会被回访，
所以换完面板要手动跑一次 `mode:'full'`。

## 9. 后台

### 9.1 三个角色，白名单放行

`bff/src/adminauth.js`。原来只有两个**共用口令**（一个平台的、一家酒店一个），
能进来就等于是那个角色 —— 没有「谁」这个概念：前台三个人共用一个密码，出了事
查不出是谁动的，人走了也没法只收回他一个人的权限。

| 角色 | 管得着 |
|---|---|
| `platform` | 全部。建店删店、划盒子、面板、平台商户 |
| `manager` | 自己这一家：品牌、背景、菜单、收款、受限板块、房间、订单 |
| `desk` | 只有房间和订单：开房、退房、填房号、接单 |

**是白名单，不是黑名单**（`DESK_ALLOWED`，方法 + 路径）：以后新加的接口，前台
**自动**够不着。这一条是设计上的选择 —— 黑名单的形状是「每加一个接口都要记得
去补一行」，而忘记补的那一次不会报错。

界面上藏按钮是体验，**权限是服务端按路由拦** —— 两者差一个 F12。有一条接口是
「填房间号」和「换线路」共用的（同一个 body 的不同字段），所以路由里把 `desk`
传来的线路字段**剥掉**：否则一个会按 F12 的前台可以把某间房换成别的片单。

### 9.2 会话、限速、记录

- **登录换一张有期限的票**，浏览器里存的是票不是密码；票能吊销（改密码 =
  之前发出去的票全作废；停用账号 = 他手里的票当场失效）。库里存 sha256。
- **登录限速**：错五次开始要等，错得越多等得越久（前台手滑是常事，所以前四次
  不拦）。原来这个控制台挂在公网域名上，密码是可以无限次猜的。
- **操作记录**：谁、什么时候、动了哪一家的什么。**只记写操作**，读的不记；
  密钥类字段（`token|password|secret|pin|key`）只记名字不记值。

### 9.3 三个界面

| 地址 | 谁用 | 形状 |
|---|---|---|
| `/admin/` | 平台 + 酒店 | 单文件 HTML，左导航 + 12 页（总览、房间、服务、周边、外观、品牌、电视、受限、收款、账号、记录、酒店、面板），hash 路由，按角色显隐 |
| `/desk/` | 酒店前台 | 单文件 HTML，手机上站着用：开房、退房、接单 |
| `/download` | 装机的人 | 二维码、版本、大小、SHA-256、装机步骤，全部从磁盘上那个 APK 现算 |

> **`last_seen` 的语义是「最后开机」，不是「在线」** —— `hello` 一次开机只调
> 一次。所以房间页的筛选写的是「7 天没开机」而不是「离线」，而要看当下状态的
> 地方走 `/api/device/state`（这一条**故意不更新** `last_seen`，否则轮询会把
> 那一列变成一片「刚刚」）。

## 10. 自检脚本

没有单元测试框架，有五个会把自己跑一遍的脚本。**改完必须跑，五个都要绿。**

```bash
cd bff
node scripts/selfcheck.js       # 88 项：收款、发货、防重复发货
node scripts/tenancy-check.js   # 142 项：A 店看不看得见 B 店的东西
node scripts/ui-check.js        #  6 项：后台/前台那两个单文件页面还能不能跑
node scripts/auth-check.js      # 49 项：角色能不能、票活不活、限速、记录
node scripts/api-auth-check.js  # 50 项：**真起一个服务、真发 HTTP** 去撞门
```

每一个都补一个具体的洞：

- **`tenancy-check`** 尤其重要。多租户的错误**线上不会报错**，只会是 B 店的客人
  发现电视上写着别人家的名字，或者一家交了钱十家一起免费。只能主动去撞。
- **`ui-check`**：`/admin/` 和 `/desk/` 是「一个 HTML 里塞一整段内联 JS」，没有
  构建步骤，**发布前没有任何东西会解析它**。写错一个字符，服务端照样 200 把
  文件发出去，浏览器解析到那一行整段放弃 —— 页面一片空白，而所有 curl 检查全绿。
  真出过一次：少一个 `=`。
- **`auth-check` 和 `api-auth-check` 的分工**：前者查规则本身，后者查**规则有没有
  真的挂在路由前面**。两者差的正是「前台点不到」和「前台调不到」之间那道缝 ——
  而只有后者才是权限。

## 11. 陷阱（接手的人最该先看这一节）

1. **改 `.env` 的 `XUI_BASE` 不会换面板。** 真正生效的是 `panels` 表里
   `slug='default'` 那一行的 `api_base` —— 默认面板只在第一次启动时从环境变量
   建出来（`if exists return`），之后改 `.env` 不动它。换面板要改四个地方，
   清单在 `deploy/DEPLOY.md`「把整个平台换到另一台面板」。
2. **面板的分类 id 是面板本地的。** 受限分类存的是 `vod:43` 这样的 id，不是名字。
   克隆出来的面板 id 会一致，各自独立建起来的**不会** —— 换过去之后「受限分类」
   会指向别的东西：要么把成人内容放出去，要么把正常分类锁上。切之前用
   `player_api.php?action=get_vod_categories` 两边拉下来比一遍。
3. **`XUI_BASE` 的主机名必须和面板给出的台标地址一致。** `publicAsset()` 是比
   主机名来决定要不要把图重写到我们自己域名下的；不一致就不重写，HTTPS 页面里
   混进 HTTP 图片。
4. **`ott.db` 本体可能只有 4KB。** 服务起来之后写的东西全在 `ott.db-wal` 里。
   只拷 `.db` 等于拿到一个空库，而且要到恢复的时候才发现。
5. **面板的套餐是在采集跑完的结尾才一次性更新的。** 跑到一半看
   `player_api` 数字不动，不代表没生效。
6. **升级必须用同一把签名钥匙。** 换了钥匙的包对盒子来说是另一个应用，装不上，
   只能一个房间一个房间地卸载重装。而且 Android 8 之后 ANDROID_ID 跟着签名走 ——
   换钥匙 = 所有设备号全变 = 房间、成人授权、观看权一起丢。
7. **别用 `APP_VERSION` 判断界面有没有更新。** 那是环境变量里写死的，部署不会
   动它。用服务端算出来的页面指纹。
8. **上游有明文 HTTP 和不给 CORS 头的。** 盒子的 WebView 开了
   `MIXED_CONTENT_ALWAYS_ALLOW` 所以能放；浏览器不能。从笔记本上看某个台是坏的，
   不代表电视上是坏的（`relay.js` 存在的原因）。

## 12. 跑起来

```bash
# 服务端（默认端口 9081，无 .env 也能起，所有配置都有默认值）
cd bff && npm install && npm run dev

# 电视界面
cd web && npm install && npm run dev
```

后台第一次进：`ADMIN_TOKEN` 没设的话，启动时会生成一个并写到日志里。
生产部署（Docker + nginx + TLS + 备份 + 巡检）见 `deploy/DEPLOY.md`。

要点：**nginx 上要开 HTTP/2 和 gzip**。少了这两条，一次进点播是
201KB 的 JSON 而不是 40KB，595KB 的 JS 而不是 188KB —— 在酒店的网络上这是
「能用」和「等一下」的差别。

## 13. 术语

| 词 | 意思 |
|---|---|
| **面板 panel** | 一台 XUI.one / Xtream-codes 服务器：一整套后台、片库、推流 |
| **线路 line** | 面板上的**一个账号**，决定它能看到哪些套餐、能几个房间同时看 |
| **套餐 bouquet** | 面板上的频道/影片分组。流不被勾进线路订阅的套餐就对车队不可见 |
| **酒店 property** | 多租户的一个租户。所有业务数据都挂在它下面 |
| **盒子 device** | 一台机顶盒，主键是它的 ANDROID_ID |
| **薄壳 shell** | 那个只有一个 WebView 的 APK |
| **BFF** | 这个仓库的服务端（backend for frontend） |
| **采集器 collector** | `xui-collector`，把资源站的片库写进面板 |

**面板和线路别混**：换线路是换「看到什么」，换面板是换「从哪台机器拿」。一条
线路只在它自己那台面板上有效 —— 把 A 面板的线路填给指着 B 面板的酒店，认证会
失败，那家的电视会全黑。
