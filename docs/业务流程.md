# KDTV 业务流程全书

从你进一台盒子，到客人在房间里看电视，到钱进你的账户 —— 中间每一步是什么、
谁做、在哪个界面做。

这份文档的对象是**你自己和将来接手的人**，不是客户。所以它写的是"实际怎么
运转"，不是"我们有多好"。

> 写代码的那一面在 [系统总览.md](系统总览.md)：架构、数据模型、端到端的请求
> 链路、要改一件事该动哪个文件、以及踩过的陷阱。这一份只讲「谁在哪个界面做
> 什么」。
>
> 文中的域名一律是占位符（`ott.example.com`），真值在本机的
> `deploy/SECRETS.local.md`，不进 git。

---

## 0. 先认清三个角色、三样东西

**三个角色**

| 角色 | 是谁 | 关心什么 |
| --- | --- | --- |
| **平台** | 你（KDTV） | 卖盒子、收服务费、管所有酒店、保证片源和服务器活着 |
| **酒店** | 每家酒店的前台/老板 | 自己的房间、自己的客人、自己的点餐订单 |
| **客人** | 住店的人 | 打开电视就有东西看 |

**三样东西**

| 东西 | 在哪 | 干什么 |
| --- | --- | --- |
| **XUI 面板** | 一台独立服务器 | 装着所有频道和影片。**内容的唯一来源** |
| **KDTV 服务器** | 另一台服务器（`ott.example.com`） | 规则和界面都在这。房间、订单、收款、多酒店隔离 |
| **机顶盒** | 客人房间的电视后面 | 一个壳。开机就去 KDTV 服务器要界面 |

一句话记住整个架构：

> **内容在面板，规则和界面在 KDTV 服务器，盒子只是一个壳。**

这一条决定了后面所有事情。**改界面、改菜单、改价格、换模板，都不用碰盒子** ——
改服务器，全部电视下次开机就变了。只有很少的几件事（开机自启、权限、应用名、
服务器地址）才需要重新发 APK。

## 1. 一台盒子的一生

### 1.1 进货

任何安卓机顶盒都行，条件只有两条：

- **Android 5.0 以上**（2014 年之后的盒子基本都满足）
- **能连网线或 Wi-Fi**

不需要什么特殊型号。盒子越便宜越好，因为它真的只是个壳 —— 解码是系统做的，
界面是服务器给的。

### 1.2 给盒子装 APK

三种方式，看现场条件选：

**① 盒子自己下载（推荐，不需要电脑）**

盒子上打开浏览器，输入：

```
ott.example.com/apk
```

这是个短地址，用遥控器敲得动。装完在应用列表里找 **KDTV**。

装机页 `ott.example.com/download` 上有二维码、版本号、文件大小和装机步骤，
手机扫一扫也能下。

**② U 盘**

把 APK 拷到 U 盘，插盒子，用文件管理器点开安装。适合一次装一批。

**③ adb（你自己批量预装时用）**

```bash
adb connect <盒子IP>:5555
adb install -r KDTV.apk
```

> **注意：升级必须用同一把签名钥匙出的包。** 换了钥匙的包对盒子来说是"另一个
> 应用"，装不上去，只能先卸载 —— 那意味着要跑一趟每个房间。钥匙放在
> `<keystore 目录>/`，**丢了就再也发不出能覆盖升级的包**。

### 1.3 盒子第一次开机

盒子开机 → 打开 KDTV → 屏幕上出现一个**六位配对码**。

这时候它还什么都看不了 —— 它只知道自己的设备号，不知道自己属于哪家酒店、
哪个房间。

客人永远不需要输入服务器地址。地址是烧在 APK 里的唯一一样东西。

### 1.4 在后台把它绑到房间

你（或者酒店）打开后台 → **房间和设备** → 找到那台显示配对码的新盒子 →
填上房号 → 保存。

绑好的那一刻，盒子那边会自己刷出界面：频道表、点播、客房服务全都来了。

**如果盒子有网线**，还能更省事：系统会把 MAC 地址一起报上来，你可以提前把
MAC 和房号的对应关系录好，盒子一插电就自动进对应的房间，一次交互都不需要。
装一栋楼的时候这个差别很大。

### 1.5 开机自启（让电视一通电就是 KDTV）

酒店里没人会先拿遥控器找图标。两条路，**建议两条都做**：

1. **开机广播** —— APK 里已经做好了，收到开机广播就把自己拉起来。大部分盒子
   吃这一套，不用配置。
2. **设成默认桌面** —— 装机时在系统设置里把 KDTV 设为默认启动器。
   **这条更可靠，而且顺带挡住了客人乱逛系统设置** —— 酒店真正想要的是这个。

为什么两条都要：Android 10 之后收紧了"后台启动应用"，有些固件会把第一条
**静默拦掉**，不报错，只是什么都没发生。装机的人不会知道，直到第二天有客人
说电视打不开。第二条不受这个限制。

如果盒子上已经有一个系统自带的桌面抢着当 Home，装机时要把它禁掉
（`adb shell pm disable-user <那个桌面的包名>`）。

### 1.6 盒子坏了 / 换房间

- **换房间**：后台改一下这台盒子的房号就行，不用碰盒子。
- **换新盒子**：新盒子出配对码 → 绑到那个房间 → 旧的在后台删掉。
- **恢复出厂**：设备号会变，等于一台新盒子，重新绑。

## 2. 内容从哪里来

```
资源站 ──采集──▶ XUI 面板 ──线路──▶ 盒子
                    │
              频道、电影、剧集
```

- **直播频道**：面板里配好的源，目前 91 个台。
- **电影和剧集**：用采集器从资源站抓进面板。面板上现在 6745 部电影、749 部剧集
  （13318 集），电视上能看到的非成人片库 1658 部（2026-09-20）。

**线路（line）**是面板里的一个账号，决定"这台盒子能看到哪些内容"。

默认所有酒店共用同一套线路 —— 大家看到一样的频道表，管起来最省事。
需要的时候可以给某家酒店单独配一条线路：比如一家中资酒店要多几个国内台，
一家日资酒店要日本台。**在后台那家酒店的设置里填上它自己的线路账号即可，
不影响别家。**

> 视频是**盒子直接找面板要**的，不经过 KDTV 服务器 —— 否则我们的服务器带宽
> 会变成瓶颈。只有极少数台（源站不允许浏览器直接取的）会绕一下我们的服务器，
> 那几个台在排查文档里单独列着。

### 面板是可以换的，但换得动的只有一半

KDTV 取内容只用 **Xtream Codes 标准接口**（`player_api.php`，加
`/live/ /movie/ /series/` 三种播放地址），没有用任何 XUI.one 私有的东西。
所以**任何 Xtream 兼容的面板都能接**——XUI.one、XtreamUI、Xtream Codes 老版本
都算。换面板要改三处：`XUI_BASE`、`XUI_PUBLIC_BASE`，以及 nginx 里 `/stream/`
指向哪台机器。

两个**换不动**的地方，先知道再决定：

1. **采集器只认 XUI.one。** 它是直接写面板的 MySQL 表、再触发面板的
   `cache_engine.php`，不是走接口。换成别家面板，采集这条线要重写。
   ——**接别人的面板就等于没有采集，片库由对方说了算。**
2. **一台 KDTV 服务器只能接一个面板。** 面板地址是全局配置。
   *线路*可以一家酒店一条，*面板*不行。真要 A 店一个面板、B 店另一个，
   得把面板地址挪进酒店表里，是改代码。

### 一条线路能同时看几个房间

**线路上的 `max_connections` 就是并发上限**，因为一家酒店所有房间共用一条线路。

自己的面板可以把这个数开得很大（现在这条是 **500**）。
**外面买来的线路通常只给 1–5 个并发** —— 那种线路开到第二个房间就会互相踢。
所以"买条线路接上就能开酒店"这条路走不通，除非对方肯按房间数给并发。

## 3. 客人在电视上能做什么

**两套界面模板，按酒店选**（后台 → 电视端 → 界面模板，盒子下次开机生效）：

| 模板 | 开机看到的 | 适合 |
| --- | --- | --- |
| **酒店门户**（默认） | 宫格首页，直播是其中一格 | 度假酒店 —— 客人会去翻点播、点餐 |
| **直播优先** | 正在播的那个台，全屏 | 商务酒店、长住公寓 —— 进门就是开电视 |

客人能用到的：

- **电视直播** —— 按频道号直接跳台，上下键换台，有频道列表和节目单
- **点播** —— 电影和剧集，**支持拼音首字母搜索**（打 `sywj` 找到《深渊无间》，
  因为片库里九成是中文片名，客人手上只有遥控器）
- **客房服务** —— 在电视上点餐、点客房用品，下单后前台的手机会响
- **酒店信息** —— 酒店自己填的介绍、电话、Wi-Fi 密码等
- **成人区**（可选） —— 默认关闭；开了的话要输 PIN 才进得去，
  没开通的房间**连这个入口都看不见**
- **多语言** —— 中文、英文、高棉文、印尼文

## 4. 钱怎么走

这是最容易搞混的一块，所以先给结论：

### 三条钱线，互不相干

| 谁付钱 | 付什么 | 进谁的账户 |
| --- | --- | --- |
| **酒店 → 你** | 服务费（按月/季/年） | **你的商户** |
| **客人 → 你** | 买观看权（按天，绑这台盒子） | **你的商户** |
| **客人 → 酒店** | 客房服务点餐 | **这家酒店自己的商户** |

**点餐的钱直接进酒店自己的商户，不经过你的账户。** 这是当初定下的口径，
理由很实在：钱经你手一道，你就要给十家酒店做对账和分账，还要承担资金风险。
让酒店收自己的餐费，你只收服务费，账目最干净。

所以每家酒店在后台要填**自己的 Jeepay 商户**（点餐用）。你自己的商户在平台
那一层填（服务费和观看权用）。

### 两种计费模式

**① 酒店付费（默认）** —— 酒店按期付服务费，房间里的客人什么都不用付，
电视上连收款的影子都看不见。这是正常状态。

**② 客人付费** —— 酒店不付（或者不打算付），让住客自己买观看权，按天算，
跟着这台盒子走，退房了下一个客人要重新买。

两者不是两套东西，是同一个判断的两个分支：**先看酒店付了没有，没付才看这台
盒子自己买了没有**。所以酒店服务费到期的那一刻，电视不会黑屏，只是从"免费"
变成"客人自己买"。

客人付费模式下，**默认只挡点播，不挡直播**。一台打开只有黑屏的电视，酒店第一
天就会打电话来骂，而且客人根本不会想到"原来要付钱"—— 他只会觉得东西是坏的。
直播免费、点播收费，是客人自己能看懂的分界。

### 一条安全底线

> **收不了款的时候，什么都不锁。**

支付通道没配好、密钥填错了、Jeepay 那台机器挂了 —— 这些时候如果照常上锁，
结果是整栋楼的电视都打不开，而客人连付钱的办法都没有。
**一个坏掉的收银台应该让东西免费，不是让东西消失。**

## 5. 你怎么管一家酒店

后台地址：

```
https://ott.example.com/admin/
```

用**平台总口令**登录，能看到所有酒店；用**某家酒店的口令**登录，只看得到那一家。

| 板块 | 干什么 |
| --- | --- |
| **酒店** | 新建酒店、给酒店设登录口令、指定它用哪条线路、停用/删除 |
| **房间和设备** | 绑盒子到房间、改房号、开房退房、看每台电视最后什么时候开过机 |
| **首页** | 这家酒店的名字、欢迎语、背景图或背景视频、各页配图 |
| **品牌** | Logo、开机画面、主色调 —— 电视上那套配色是跟着酒店走的 |
| **客房服务** | 菜单（名字/价格/分类/多语言）、订单、货币 |
| **电视端** | 界面模板、直播缓冲档位、排查叠层开关 |
| **成人区** | 开不开、PIN 是多少、哪些房间允许 |
| **收款** | 这家酒店的 Jeepay 商户（点餐用）；平台自己的商户在平台层 |
| **计费** | 酒店付费还是客人付费、服务费到期时间、套餐价格 |

## 6. 酒店怎么管自己的客房

### 前台手机页（日常就用这个）

```
https://ott.example.com/desk/
```

用**那家酒店自己的口令**登录。加到手机主屏，用起来跟一个 App 一样。

只有两件事，因为这是**站在柜台前单手用的**：

- **房间** —— 开房（填客人姓名）、退房、房态一眼扫完，能看到每间房的电视
  最后什么时候开过机
- **订单** —— 待处理的排前面，接单 / 完成 / 取消，**付没付一眼看得见**
  （决定送东西过去要不要顺手收钱）

有新单会震动提示。退房和取消订单会再问一遍 —— 这两个动作没有撤销。

### 后台（改设置时用）

同一个口令也能登 `/admin/`，但**只看得到自己这一家**：改菜单、改酒店名字和
照片、改自己的收款商户、看自己的订单。

**他们看不到也改不了**：别家酒店的任何东西、平台的收款商户、线路配置、
别家的房间和设备。这不是靠界面藏起来的，是服务端每一次读写都带着酒店编号 ——
即使有人直接调接口，也只能拿到自己那一份。

## 7. 你怎么管十家酒店

### 隔离边界

所有数据都带一个**酒店编号**：房间、设备、菜单、订单、公告、图片、设置、
收款配置、计费状态。**0 号是平台自己**，1 以上是各家酒店。

有一套专门的自检脚本（`bff/scripts/tenancy-check.js`，142 项）就是用来撞这条
边界的：建两家酒店、都开一个 301 房，然后逐条去试"A 能不能看见/改动 B 的东西"。
每次改动后都要跑一遍。

这类错误线上不会报错，只会是 **B 店的客人发现电视上显示的是别人家的名字**，
或者**一家交了钱十家一起免费**。只能靠主动去撞。

### 加一家新酒店的标准流程

1. 后台 → 酒店 → **新建**，填名字和标识
2. 给它**设一个登录口令**（前台拿这个登录，只看得到自己这一家）
3. 决定**线路**：默认共用；有特殊频道需求就单独填它自己的线路账号
4. 决定**界面模板**：酒店门户 还是 直播优先
5. 填**酒店名字、Logo、背景图**（客人开机第一眼看到的就是这些）
6. 填**客房服务菜单**和**货币**
7. 填**这家酒店自己的 Jeepay 商户**（点餐收款用）
8. 设**计费方式**：酒店付费（填到期时间）或客人付费
9. 装盒子 → 绑房间（见第 1 章）
10. 现场验：随便找两个房间，开机、跳台、点一单、前台手机上看得到

### 线路策略

默认**十家共用一套线路**，管起来最省事 —— 频道表统一，出问题一次修好所有人。
只在有明确理由时才单独配（某家要额外的国内台/日本台），因为每多一条线路
就多一份要维护的东西。

但**并发是按线路算的**：共用一条线路，就是十家酒店的房间一起挤这条线路的
`max_connections`。房间总数接近这个数之前，就该给大店单独拆一条出去。
怎么看这个数，见第 2 章末尾。

## 8. 出问题从哪里查

### 电视打不开 / 一直转圈

1. 盒子有网吗？（系统设置里看）
2. 后台里这台盒子**绑房间了吗**？没绑就只会显示配对码。
3. 服务器活着吗？浏览器打开 `ott.example.com` 看看。
4. 开机那几十秒网络还没通是正常的 —— 界面会自己重试一分钟，
   一分钟还不行才会显示失败画面。

### 某一个台打不开，别的台都正常

**先分清是源坏了还是我们的问题** —— 这两种处理方式完全不同：

- 后台 → 电视端 → 打开**排查叠层**，电视右上角会显示码率、带宽、缓冲、丢帧、
  直连还是走中继。丢帧高 = 盒子解不动；缓冲一直见底 = 上行不够；
  一直在重连 = 这条源本身坏了。
- **上门排查前打开，走之前关掉。**

已知有几个台是**源本身的问题**（面板里 302 过去就是 404，或者分片服务器连不上），
换什么播放器都没用 —— 这类只能在面板里换源。完整名单见
[`shell/probe/RESULTS.md`](../shell/probe/RESULTS.md)。

### 整栋楼都卡

多半是酒店的上行不够。后台 → 电视端 → **直播模式**调成「流畅优先」
（缓冲 30 秒，更不容易卡，代价是比直播慢一点）。

### 客人下了单，前台没收到

1. 前台手机页是不是登录的**那家酒店自己的口令**（不是别家的）
2. 那一页开着的时候会每 20 秒自己刷新；锁屏时不刷，解锁会立刻刷
3. 后台的客房服务页能不能看到这一单 —— 能看到就是前台页的问题，
   看不到就是下单没成功

### 收了款但订单还是"未付款"

支付回调没到。后台 → 收款 → **对账**，手动拉一次。
如果经常这样，检查 Jeepay 那边配的回调地址能不能从外网访问到我们的服务器。

## 9. 开一家新酒店的清单

照着勾，全勾完才算能交付：

- [ ] 后台建好酒店，名字填的是**酒店真名**，不是默认的 KDTV
- [ ] 给酒店设了**登录口令**，并且告诉了前台
- [ ] 选好**界面模板**（门户 / 直播优先）
- [ ] 传了酒店的 **Logo、开机图、背景图**
- [ ] **客房服务菜单**是这家酒店真实的菜单，**货币对**
- [ ] 填了这家酒店**自己的 Jeepay 商户**，并且用小额真实付款测过一笔
- [ ] 平台自己的 Jeepay 商户也填了（服务费、观看权用）
- [ ] 确定了**计费方式**和到期时间
- [ ] 成人区：**不用就关掉**；要用就改掉默认 PIN
- [ ] 每个房间的盒子都**绑好房号**，房号和门牌对得上
- [ ] 每台盒子都设了**开机自启**（默认桌面那条一定要做）
- [ ] 抽两个房间**现场验**：开机 → 跳台 → 搜一部片 → 点一单 →
      前台手机上看得到这一单
- [ ] 前台**当面教过一遍**：怎么开房、怎么退房、怎么接单
